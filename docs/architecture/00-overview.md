1. AS-IS: контекст и контейнеры
1.1 Context diagram (Level 1)

   Пользователи:
  - Пациент — записывается на приём, оплачивает, смотрит анализы, загружает документы
  - Врач — ведёт приём, смотрит карту пациента, вносит диагнозы/назначения
  - Администратор клиники — управляет расписанием, обрабатывает обращения

Внешние системы:
  - Платёжный шлюз — обработка онлайн-оплаты
  - Лаборатория — передача результатов анализов
  - AI-сервис (LLM/OCR провайдер) — обработка документов и текста

```

  Patient[Пациент] -->|записывается, оплачивает, загружает документы| System[Платформа Здоровье+]
  Doctor[Врач] -->|ведёт приём, вносит диагнозы| System
  Admin[Администратор клиники] -->|управляет расписанием| System
  System -->|обработка платежа| Payment[Платёжный шлюз]
  System <-->|результаты анализов| Lab[Лаборатория]
  System -->|OCR + извлечение сущностей| AI[AI-сервис LLM/OCR]
```

Критерий отнесения элемента к Context vs Container: кто владеет деплоем. Своё — контейнер (Level 2). Чужое, недоступное для управления — внешняя система (Level 1).

1.2 Container diagram (Level 2)
1. Web-приложение (React) — запись, анализы, оплата
2. Mobile-приложение (React Native) — то же с телефона
3. CRM (Salesforce/самописная) — история обращений, маркетинг
4. ERP/1С — финансы, учёт медикаментов, зарплата
5. MES-подобная система — расписание врачей, очереди, кабинеты
6. Core Services (логическая группа микросервисов: Patients, Visits, Prescriptions)
7. PostgreSQL — write-модель (транзакционное хранилище)
8. Kafka — брокер событий
9. Read Store (Elasticsearch) — CQRS read-модель

Связи:
- Web/Mobile → Core Services: REST, sync
- MES → Core Services: gRPC, sync
- Core Services → PostgreSQL: запись
- Core Services → Kafka: публикация событий
- Kafka → Read Store: асинхронное обновление
- CRM, ERP/1С → Kafka: подписка на события

2. Ключевые архитектурные решения текущей системы
2.1 Event-driven интеграция вместо point-to-point

   Рассмотрено:
- Point-to-point REST/gRPC — отклонено: жёсткая связанность, сбой CRM/ERP
  блокирует основной поток
- Периодическая batch-синхронизация — отклонено как основной механизм:
  неприемлемая задержка для операционных данных

Принятые издержки:
- Eventual consistency вместо мгновенной согласованности
- Требование идемпотентности от потребителей (at-least-once delivery)
- Операционная сложность: мониторинг лага, schema registry

2.2 Saga через оркестрацию (сценарий «Запись на приём»)

Шаги: бронь слота (MES) → оплата (Payment) → создание визита (Core) → уведомление

Рассмотрено:
- Хореография — отклонено: размытая ответственность за 4-шаговый процесс
  усложняет диагностику "на каком шаге зависла запись"

Принятые издержки:
- Orchestrator — дополнительная точка отказа
- Риск избыточного знания о внутренней логике шагов — митигируется вызовом
  только публичных API

Компенсации: Payment.Refund, MES.ReleaseSlot

2.3 CQRS с read-моделью в Elasticsearch

Рассмотрено:
- Прямое чтение из Postgres/реплик — отклонено: не решает проблему формы
  данных для сложных агрегаций, нет полнотекстового поиска
- Materialized views в Postgres — отклонено: недостаточно гибко
- MongoDB — отклонено в пользу Elasticsearch: ключевой read-сценарий —
  полнотекстовый поиск по содержимому документов после OCR+LLM

Принятые издержки:
- Eventual consistency между write- и read-моделью
- Elasticsearch не источник истины — пересобирается из событий/Postgres

3. Сценарий 1: прогнозная аналитика загрузки — оценка
Идея: AI анализирует исторические данные (сезонность, день недели, время
суток, популярность врачей), строит прогноз загрузки, предлагает
оптимальное расписание.

Статус: рассмотрено и приоритизировано ниже сценария 2

Обоснование:
- Задача класса time-series/классический ML, а не LLM-задача — иной набор
  компетенций и рисков валидации (data drift, точность прогноза), чем
  у OCR+LLM извлечения сущностей
- Ниже непосредственный ROI на MVP-горизонте по сравнению со сценарием 2:
  снижение ручного ввода данных даёт более быстрый и измеримый эффект,
  чем оптимизация расписания
- Рекомендация: реализовать отдельным этапом после MVP сценария 2,
  с привлечением компетенций по ML-моделированию временных рядов

4. Сценарий 2: OCR+LLM обработка документов
4.1 Архитектурные развилки TO-BE

Синхронно или асинхронно. Обработка документа (OCR + LLM) занимает секунды и зависит от внешнего провайдера. Решение: загрузка отделена от обработки — 202 Accepted сразу, статус документа асинхронно меняется в UI.

Saga или нет. Это не Saga: шаги (сохранить → распознать → извлечь → записать) — последовательный конвейер обработки одного артефакта в одном бизнес-контексте, а не независимые транзакции с денежными/юридическими эффектами, требующими компенсации. Это event-driven pipeline с retry и state-machine статусов документа.

Human-in-the-loop. LLM может ошибаться в дозировках/диагнозах. Извлечённые данные попадают в статус «черновик / pending_review» — только подтверждение врача переводит их в официальную запись визита.

4.2 Sequence diagram (TO-BE)
1. Пациент загружает скан через Web/Mobile
2. Document Upload Service → сохраняет файл в MinIO, создаёт запись
   в Postgres (status=uploaded), возвращает 202
3. → публикует DocumentUploaded в Kafka (ключ партиции: document_id)
4. OCR Worker слушает → извлекает текст → DocumentTextExtracted / OcrFailed
5. LLM Extraction Worker слушает → вызывает DeepSeek → извлекает сущности
   → DocumentEntitiesExtracted / ExtractionFailed
6. Core Services слушает → записывает в Postgres (status=pending_review)
7. → публикует DocumentReadyForReview
8. Read Store (Elasticsearch) индексирует документ (даже в pending_review)
9. Врач подтверждает/отклоняет → status=confirmed → DocumentConfirmed
   → обновление индекса

Ошибки на шагах 4,5: *Failed-событие → status=needs_manual_review,
файл не теряется (остаётся в MinIO)

4.3 Решение
Рассмотрено:
- Синхронная обработка — отклонено: недопустимая задержка UX, хрупкость
  при сбое AI-провайдера
- Saga с компенсациями — отклонено: не независимые бизнес-транзакции
- Авто-запись без подтверждения врача — отклонено: неприемлемый риск
  для медицинских данных

Принятые издержки:
- Задержка до "ready for review"
- Пять асинхронных шагов вместо одного синхронного вызова — требует
  сквозного трейсинга по document_id
  
5. AI-ассистент с tool calling — архитектура (без реализации)
 Идея: LLM-агент поверх внутренних микросервисов Core Services, выступает
как tools для персонала/пациентов (например, "покажи расписание врача X",
"перенеси визит пациента Y").

Модель авторизации:
- Read-only tools (просмотр расписания, статуса документа) — доступны
  агенту без дополнительного подтверждения
- Write tools (перенос визита, отмена записи) — требуют явного
  подтверждения пользователем перед выполнением, агент не может
  выполнить действие с необратимым эффектом автономно

Статус: спроектировано на уровне архитектуры, не реализовано в MVP —
решение оставить как чисто консалтинговый раздел, чтобы не смещать
фокус проекта в сторону разработки агентов

6. Комплаенс: 152-ФЗ и защита медицинских данных
Требования, применимые к архитектуре:
- Особая категория данных (сведения о здоровье) — требует отдельного
  оформленного согласия субъекта
- Локализация первичного сбора (ч.5 ст.18) — первичный сбор только на
  серверах в РФ; с 01.07.2025 сбор через зарубежные базы прямо запрещён.
  Выполняется автоматически: PostgreSQL и MinIO в нашей архитектуре
  и так в российском периметре
- Трансграничная передача (ст.12) — вызов DeepSeek API (КНР) — это
  трансграничная передача. Требует: отдельное согласие с указанием
  страны, уведомление Роскомнадзора до начала передачи, оформление
  поручения обработки. Китай включён в перечень стран с адекватной
  защитой — передача возможна сразу после уведомления, без ожидания
  10 рабочих дней, которое требуется для стран вне перечня

Решение: LLM Extraction Worker вызывает DeepSeek API

Рассмотрено:
- Российский провайдер (YandexGPT/GigaChat) — не выбран для MVP
  (доступность/стоимость пет-проекта), зафиксирован как production-
  альтернатива, полностью снимающая вопрос трансграничной передачи
- Локально развёрнутая открытая модель — отклонено как избыточное
  для MVP по срокам/ресурсам

Митигация на уровне архитектуры (реализовано в MVP):
- В LLM-запрос передаётся только обезличенный текст документа +
  internal document_id, без ФИО и прямых идентификаторов
- Сопоставление с пациентом происходит только внутри периметра РФ

### 7. Сводный decision log

 

| Решение | Отклонённые альтернативы | Ключевая издержка |
|----|----|----|
| Event-driven интеграция (Kafka) | Point-to-point, batch-sync | Eventual consistency |
| Saga через оркестрацию | Хореография | Orchestrator — точка отказа |
| CQRS + Elasticsearch | Прямое чтение, MongoDB | Индекс не источник истины |
| Async pipeline (не Saga) для документов | Sync-обработка, Saga | Задержка до review |
| Human-in-the-loop перед записью в карту | Авто-запись | Дополнительный шаг для врача |
| DeepSeek (с митигацией) | YandexGPT/GigaChat, self-hosted | Требует процедуры ТГП |
